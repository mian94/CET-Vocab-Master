## 3. 发现的问题

### 🔴 P0 — 阻塞开发，必须在编码前解决

#### 问题 #1：AI 生成后保存流程未定义

**现象：** dev.md 第 2.2 节数据流写道"生成完成 → POST 保存到 /api/articles（标记为 custom 类型）"，但第 4.2 节中 `POST /api/articles` 的权限标注为"管理员"。普通用户无法调用此接口。

**影响：** 验收标准 3-1 要求"该文章会自动添加至用户的'我的定制'目录中"，当前设计无法实现。

**需要明确：**
- 是为用户新建一个 `POST /api/articles/custom` 接口（权限为普通用户）？
- 还是在 `/api/generate` 接口内部，生成完成后由后端自动保存，一并返回文章 ID？

#### 问题 #2：从文章选词的跨页面数据传递未设计

**现象：** 验收标准 3-2 的流程是"用户在阅读页勾选单词 → 点击'用这些词生成' → 跳转到 /generate 页面"。dev.md 中 `pages/read/[id].vue` 和 `pages/generate.vue` 是两个独立页面，但未说明选中的单词如何从阅读页传递到生成页。

**需要明确：**
- 通过 URL query 参数传递（如 `/generate?words=sustainable,innovation,advocate`）？
- 通过 Pinia store 临时存储？
- 通过 sessionStorage？

#### 问题 #3：管理端删除操作缺少确认机制

**现象：** 验收标准 5-4 明确要求"管理员确认删除操作"，但 dev.md 第 7 节组件列表中没有 `ConfirmDialog` 或类似的确认弹窗组件。

**需要明确：** 使用 `window.confirm()` 原生弹窗，还是设计一个自定义确认弹窗组件？

### 🟡 P1 — 不阻塞开发，但需要在开发过程中补充

#### 问题 #4："我的定制"库在侧边栏中的展示未设计

**现象：** PRD FR-3.3 要求"生成后的文章自动保存至用户的'个人定制库'"，验收标准 3-1 要求"自动添加至用户的侧边栏'我的定制'目录中"。但 dev.md 第 6.1 节的侧边栏布局只展示了预置文章目录，没有"我的定制"分区。

**影响：** 用户无法在侧边栏中看到自己生成的 AI 文章。

**建议：** 在 Sidebar 组件中增加一个 Tab 或分组，展示 `type: 'custom'` 且 `author` 为当前用户的文章列表。

#### 问题 #5：词汇列表分页的前端交互未设计

**现象：** dev.md 第 4.3 节词汇接口支持 `limit` + `offset` 分页，四六级高频词汇可能有数千条。但 `/generate` 页面的 WordSelector 组件未说明如何处理大量词汇的加载——是无限滚动、分页按钮、还是全量加载？

**建议：** 采用无限滚动（infinite scroll）方案，@vueuse/core 的 `useIntersectionObserver` 可以轻松实现。初始加载 50 条，滚动到底部自动加载下一批。

#### 问题 #6：文章内容格式未定义

**现象：** dev.md 第 3.2 节 Article 的 `content` 字段标注为"纯文本或 Markdown"，但未明确到底是哪种格式。这影响 ArticleReader 组件的渲染方式——纯文本用 `<p>` 换行即可，Markdown 需要解析器（如 markdown-it）。

**建议：** 统一为 Markdown 格式。管理员上传文章时使用 Markdown 语法，前端渲染时用 markdown-it 解析。Markdown 对管理员更友好（支持加粗、标题等），且可以无缝处理段落换行。

#### 问题 #7：Prompt 模板匹配逻辑过于简单

**现象：** dev.md 第 4.5 节的模板匹配逻辑是 `{ topicTags: { $in: [topic] } }`，即精确匹配用户输入的主题词与模板的 topicTags。但用户输入的是自由文本（如"科技与环保"），模板标签是 `["#环境保护"]`，两者不会精确匹配。

**建议：**
- 方案 A：主题输入框改为从管理员预设的快捷标签中选择（不做自由文本输入），确保精确匹配
- 方案 B：保留自由文本输入，但 Prompt 中不依赖模板匹配，改为将所有模板作为参考示例传入（简单但 token 消耗大）
- 方案 C：对用户输入做关键词提取后再匹配（增加复杂度）

#### 问题 #8：管理员编辑/删除文章时，管理端列表交互未设计

**现象：** dev.md 第 7.2 节的 `ArticleForm` 是创建/编辑表单组件，但管理端 `admin/articles.vue` 页面的整体交互未描述——是表格列表 + 操作按钮？卡片布局？是否有搜索/筛选？

**建议：** 管理端文章列表采用表格布局（标题、等级、标签、操作按钮），操作按钮包含编辑和删除。词库和模板管理同理。

#### 问题 #11：Sidebar 缺少"我的定制"Tab 设计

**现象：** PRD FR-3.3 要求"生成后的文章自动保存至用户的'个人定制库'"，验收标准 3-1 要求"自动添加至用户的侧边栏'我的定制'目录中"。但 dev.md 第 6.1 节的侧边栏布局只有预置文章目录，没有"我的定制"分区。虽然 `/api/generate` 已改为后端自动保存，但前端侧边栏如何展示用户自定义文章仍未设计。

**建议：** Sidebar 组件顶部增加两个 Tab（`预置文章` | `我的定制`），默认选中"预置文章"，AI 生成完成后自动切换到"我的定制"并高亮新文章。

#### 问题 #12：TopicInput 组件描述与最终方案不一致

**现象：** dev.md 第 7.1 节 TopicInput 组件描述为"主题输入框 + 快捷标签选择"，但最终方案已确认去掉自由文本输入，改为仅从管理员预设的标签中选择。组件描述未同步更新，开发时可能产生歧义。

**建议：** 将 TopicInput 描述更新为"主题标签选择器（下拉列表展示管理员预设的 topicTags）"。

#### 问题 #13：管理端页面缺少表格列定义

**现象：** dev.md 第 7.2 节定义了 ArticleForm、VocabForm、TemplateForm 表单组件，但管理端三个页面（articles.vue、vocabulary.vue、templates.vue）的列表布局和表格列定义未说明。开发时需要逐个决定列名、宽度、排序方式等。

**建议：** 提前定义各管理页面的表格列结构：
- 文章管理：序号、标题、等级、标签、操作（编辑/删除）
- 词库管理：单词、音标、释义、等级、操作（编辑/删除）
- 模板管理：标题、标签、操作（编辑/删除）

#### 问题 #14：文章渲染管线的 SSR 兼容性未说明

**现象：** dev.md 第 10.4 节的高亮逻辑使用 `document.createTreeWalker`，该 API 仅在浏览器端可用。dev.md 末尾有 SSR 兼容提示，但未说明 ArticleReader 组件在 SSR 阶段如何处理——是跳过高亮只渲染 Markdown？还是整个组件设为客户端渲染？

**建议：** ArticleReader 的高亮逻辑包裹在 `onMounted` 或 `process.client` 条件中。SSR 阶段先渲染纯 Markdown HTML（无高亮），客户端 hydration 后再执行高亮替换。用户感知上无差异（首屏即有高亮），因为 hydration 在毫秒级完成。

#### 问题 #15：Vocabulary 的 word 唯一索引需改为复合索引

**现象：** dev.md 第 3.3 节 Vocabulary 的索引定义为 `word`（唯一）+ `{ word, level }`（复合）。如果同一单词在四级和六级中释义不同（如 "address" 在四级是"地址"，六级是"处理"），`word` 唯一索引会导致第二个词条插入失败。

**建议：** 移除 `word` 唯一索引，仅保留 `{ word, level }` 复合唯一索引。同一单词可以在不同级别中各存在一条记录。

### 🟢 P2 — 锦上添花，MVP 后迭代

#### 问题 #9：首次访问的引导体验未设计

**现象：** 新用户注册成功后跳转到"阅读首页"，但如果管理员尚未上传任何文章，侧边栏为空，主内容区为空，用户体验差。

**建议：** 空状态时展示引导提示（如"暂无文章，管理员正在准备中"）。

#### 问题 #10：AI 生成的 Prompt 未考虑无模板匹配的兜底

**现象：** 如果用户输入的主题没有匹配到任何模板，`template` 变量为 `null`，Prompt 中的"范文参考"部分会缺失。

**建议：** 在 Prompt 组装逻辑中增加兜底——无模板时跳过"范文参考"部分，或使用一个默认的通用模板。

### 高亮匹配的边界情况

dev.md 第 10.4 节的正则 `\b(word1|word2)\b` 存在以下边界问题：

- **大小写敏感：** 使用 `gi` 标志解决，但替换后的 `<mark>` 标签会丢失原始大小写。需要在 replace 回调中保留原文。
- **词形变化：** 用户文章中可能出现 "sustainable" 的名词形式 "sustainability"，当前正则无法匹配。MVP 阶段可以接受（只匹配原形），后续可考虑词干提取。
- **HTML 标签冲突：** 如果文章内容包含 HTML 标签（如 Markdown 渲染后的 `<strong>`），正则可能误匹配标签内的文本。需要先渲染 Markdown，再对纯文本节点做高亮匹配。
