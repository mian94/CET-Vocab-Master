# 架构设计与目录结构 — 待决事项与推荐方案

本文档列出 `stack.md` 中架构设计和目录结构存在的问题，每个问题提供可选方案和推荐方案，供确认后纳入开发文档。

## 1. 管理员登录方式

### 问题

当前目录结构中 `server/api/auth/` 只有一套 `login.post.ts`，未区分管理员和普通用户的登录入口。

### 方案对比

| | 方案 A：共用登录接口 | 方案 B：独立登录接口 |
|---|---|---|
| **接口设计** | `/api/auth/login` 统一登录，登录成功后返回 `role` 字段，前端根据角色跳转 | 管理员走 `/api/admin/login`，普通用户走 `/api/auth/login`，两套独立逻辑 |
| **数据库** | `users` 集合中 `role` 字段区分 `admin` / `user` | 同左，`role` 字段仍然需要 |
| **前端逻辑** | 登录页一个，登录成功后判断 `role === 'admin'` 则跳转 `/admin` | 管理员访问 `/admin` 时展示独立的管理员登录页 |
| **安全性** | 需在管理端路由加中间件校验 `role`，防止普通用户访问 | 接口天然隔离，中间件只校验 token 即可 |
| **开发量** | 少一个接口和一个登录页 | 多一个接口和一个登录页 |
| **扩展性** | 未来若管理员人数增加，只需改 `role` 权限逻辑 | 未来若增加多级管理员，需重构权限体系 |

### 推荐方案：A — 共用登录接口

理由：
- 管理员只有你一个人，不需要复杂的权限隔离
- 共用接口减少重复代码，维护一套登录逻辑即可
- 安全性通过管理端路由中间件（校验 `role` 字段）完全可以保障
- 管理员访问 `/admin` 时，若未登录或 `role !== 'admin'`，跳转到统一登录页并附带提示

## 2. 管理端鉴权中间件

### 问题

当前只有 `server/middleware/auth.ts`，缺少管理员鉴权逻辑。

### 方案对比

| | 方案 A：单中间件 + 角色判断 | 方案 B：双中间件分层 |
|---|---|---|
| **设计** | `auth.ts` 统一处理 token 校验，管理端路由（`/api/admin/*`）在 handler 内部额外判断 `role` | `auth.ts` 校验 token，`admin.ts` 校验角色，管理端路由挂载两个中间件 |
| **代码量** | 少一个文件 | 多一个文件，职责更清晰 |
| **可维护性** | 角色判断逻辑散落在各 handler 中 | 角色判断集中在 `admin.ts`，修改一处即生效 |
| **错误提示** | 各 handler 各自返回错误，提示可能不统一 | 统一在 `admin.ts` 返回 403，提示一致 |

### 推荐方案：B — 双中间件分层

理由：
- `auth.ts` 只负责 token 解析和用户注入（所有接口共用）
- `admin.ts` 只负责角色校验（管理端接口专用）
- 职责单一，后续若需要增加权限层级（如编辑、审核），只需扩展 `admin.ts`
- Nuxt 3 支持在 `server/middleware/` 下按文件名自动注册，也支持在路由级别通过 `defineEventHandler` 链式调用

## 3. 管理端首页内容

### 问题

`admin/index.vue` 的定位不明确，架构图标注为"管理端首页"但未定义具体展示内容。

### 方案对比

| | 方案 A：导航入口页 | 方案 B：数据统计面板 |
|---|---|---|
| **内容** | 三个卡片/按钮，分别跳转到文章管理、词库管理、AI 模板管理 | 展示文章总数、词汇总数、模板总数、最近更新时间等统计数据 |
| **开发量** | 极少，一个静态页面 | 需要额外的统计 API 和数据聚合逻辑 |
| **实用性** | 够用，管理员直接点进想管理的模块 | 有总览感，但单人管理时价值有限 |
| **扩展性** | 后续可平滑升级为统计面板 | 一步到位，但初期可能过度设计 |

### 推荐方案：A — 导航入口页

理由：
- 管理员只有你一个人，不需要数据驾驶舱
- 初期内容少（几篇文章 + 几百个词汇），统计数字没有决策价值
- 开发成本极低，快速可用
- 后续需要时可平滑升级为统计面板，不影响已有功能

### ✅ 最终方案：轻量级数据看板 + 快捷操作入口

结合方案 A 和方案 B 的优点，管理端首页展示以下内容：

**数据看板区域：**
- 当前总文章数（四级 x 篇，六级 x 篇）
- 注册用户总数
- AI 定制文章生成总次数（用于监控大模型 API 调用成本）

**快捷操作入口区域：**
- 三个卡片/按钮，分别跳转到文章管理、词库管理、AI 模板管理

开发量可控：只需 3 个简单的 count 查询（文章数、用户数、生成次数），不需要复杂的数据聚合。

## 4. 页面路由与登录/注册结构

### 问题

当前 `pages/index.vue` 标注为"首页/登录"，注册和登录的页面结构不明确。

### 方案对比

| | 方案 A：登录注册分页 | 方案 B：登录注册同页 |
|---|---|---|
| **URL** | `/login` + `/register` 两个独立页面 | `/` 首页即登录页，登录框内切换到注册模式（Tab 切换） |
| **用户体验** | 页面职责清晰，URL 语义明确 | 减少页面跳转，注册到登录切换更流畅 |
| **代码结构** | `pages/login.vue` + `pages/register.vue` | `pages/index.vue` 内含登录/注册两个表单组件 |
| **路由守卫** | 需配置未登录时跳转 `/login` | 需配置未登录时停留在 `/` |

### 推荐方案：B — 登录注册同页

理由：
- 本项目页面少（阅读页、AI 定制页），不需要复杂的路由层级
- 登录和注册表单字段高度相似（用户名/手机号/密码），同页 Tab 切换是常见模式
- 减少页面数量，降低路由配置复杂度
- 已登录用户访问 `/` 时自动跳转到阅读首页

## 5. 布局组件（layouts/）

### 问题

缺少 `layouts/` 目录，用户端和管理端的布局不同，需要独立的布局组件。

### 方案对比

| | 方案 A：Nuxt layouts 目录 | 方案 B：组件内手动包裹 |
|---|---|---|
| **实现方式** | `layouts/default.vue`（用户端）、`layouts/admin.vue`（管理端），页面通过 `definePageMeta({ layout: 'admin' })` 指定 | 每个页面手动引入 `<AdminLayout>` 或 `<UserLayout>` 组件包裹 |
| **Nuxt 集成** | 原生支持，开箱即用 | 需手动管理，每个页面重复引入 |
| **代码复用** | 布局逻辑集中在 layouts 文件中 | 布局逻辑分散在各页面中 |

### 推荐方案：A — Nuxt layouts 目录

理由：
- Nuxt 3 原生支持 `layouts/`，是框架推荐的最佳实践
- 用户端默认布局（顶部导航 + 侧边栏）和管理端布局（左侧菜单 + 右侧内容区）差异大，分开管理更清晰
- 通过 `definePageMeta` 声明式指定布局，代码最简洁

## 6. 发音音频方案

### 问题

FR-2.3 要求"点击发音图标播放英/美式读音"，但架构图和目录结构中均未体现。

### 方案对比

| | 方案 A：Web Speech API | 方案 B：第三方音频 API |
|---|---|---|
| **实现方式** | 浏览器内置 `SpeechSynthesis` 接口，无需外部服务 | 调用有道/Forvo 等 API 获取单词发音音频文件 URL |
| **成本** | 免费 | 有道 API 有免费额度，Forvo 需付费 |
| **音质** | 一般，不同浏览器/设备效果不同 | 好，真人录音或高质量合成 |
| **离线可用** | 部分浏览器支持离线 | 不可离线 |
| **开发量** | 极少，一个 composable 封装即可 | 需要 API 对接、音频 URL 缓存、错误处理 |
| **中英文支持** | 英文发音可用，中文 TTS 也可用 | 需确认 API 是否支持 CET 词汇全覆盖 |

### 推荐方案：A — Web Speech API

理由：
- 免费、零外部依赖、开发量最小
- 四六级词汇都是常见英文单词，Web Speech API 的英文发音质量完全够用
- 后续如果对音质有更高要求，可以平滑切换到第三方 API，composable 接口不变
- 需要在 `composables/` 中新增 `useAudio.ts` 封装发音逻辑

## 7. SSE 实时同步的触发机制

### 问题

架构图中有 `/api/sync` 接口，但未说明 SSE 推送是由管理员 CRUD 操作自动触发，还是需要管理员手动触发。

### 方案对比

| | 方案 A：CRUD 自动触发 | 方案 B：手动触发推送 |
|---|---|---|
| **实现方式** | 管理端的 `articles.post.ts`、`articles.[id].put.ts`、`articles.[id].delete.ts` 等接口内部，在数据库操作成功后自动调用推送函数 | 管理员 CRUD 操作只更新数据库，推送由独立接口 `/api/sync/notify` 触发，或由定时轮询检测变更 |
| **实时性** | 真实时，数据库变更即推送 | 取决于触发时机，可能有延迟 |
| **代码侵入性** | 每个 CRUD 接口都需要加入推送逻辑 | CRUD 接口保持纯净，推送逻辑独立 |
| **可靠性** | 推送失败可能影响 CRUD 主流程（需要 try-catch 隔离） | CRUD 和推送解耦，互不影响 |
| **开发量** | 中等，需要在每个 CRUD 接口中加入推送调用 | 较大，需要额外的变更检测或手动触发逻辑 |

### 推荐方案：A — CRUD 自动触发

理由：
- 实时性要求明确（验收标准要求"不刷新页面的情况下"实时可见）
- 管理员只有一个人，操作频率低，不需要复杂的解耦设计
- 推送逻辑封装为工具函数（如 `utils/notify.ts`），CRUD 接口中一行调用即可，侵入性可控
- 推送失败用 try-catch 包裹，不影响 CRUD 主流程，只记日志

### ✅ 最终方案：砍掉管理端→用户端 SSE，依赖前端缓存刷新

**MVP 阶段彻底移除 `/api/sync` 接口。** 理由：

- 管理员更新文章不需要实时推送给正在背单词的用户，这会打断用户的"心流"，属于过度设计（Over-engineering）
- 单人管理员场景下，实时推送没有实际价值
- 前端框架自带的缓存刷新机制完全够用：在 Nuxt 3 中，`useAsyncData` / `useFetch` 在路由切换时（如从阅读页退回列表页、切换四六级）会自动重新拉取最新数据，实现"静默刷新"

**架构图修正：**
- SSE 仅限于 AI 短文定制时的流式输出（即 `/api/generate` + `useStreaming.ts`）
- 移除 `/api/sync` 接口
- 移除 `composables/useSSE.ts`（SSE 逻辑合并进 `useStreaming.ts`）
- 移除 `server/utils/notify.ts`
